### 1. Executive Summary & Objective

In regulatory and banking compliance workflows, Fixed Deposit Receipts (FDRs) pledged as security deposits by educational institutions cannot be authenticated solely through document forensics (EXIF, OCR, ELA, or visual stamps). Definitive verification requires independent reconciliation against the issuing bank's core banking records.

Phase 3.8 establishes a typed, server-side **Bank Verification Provider Gateway** for FDR Guardian AI. In accordance with strict banking security principles, this phase:
1. Defines a provider-neutral server-side contract (`BankVerificationProvider`).
2. Implements a deterministic, fixture-driven sandbox provider (`SandboxBankVerificationProvider`) for safe demonstration, automated testing, and development.
3. Enforces a **strict regulatory invariant**: Sandbox simulations must **NEVER** masquerade as live bank confirmations or become `EXTERNAL_VERIFIED`.
4. Defines a clean **Production Adapter Boundary** (`UnconfiguredProductionBankProvider`) that returns `NOT_CONFIGURED` until institutional credentials (e.g., SFMS/RBI Open Banking PKI certificates) are provisioned.
5. Persists inquiry records in `FdrBankVerificationRequest` and logs immutable audit records in `FdrAuditLog`.

### 2. Typed Provider Contract & Architecture

The provider abstraction is decoupled from UI components, route handlers, and the risk engine. All provider interactions conform to the `BankVerificationProvider` interface defined in `src/lib/fdr/types.ts`:

```typescript
export interface BankVerificationProvider {
  readonly providerKey: string;
  readonly providerName: string;
  readonly mode: BankVerificationMode; // "SANDBOX_SIMULATED" | "PRODUCTION_LIVE"

  verifyInstrument(
    params: BankVerificationRequestParams
  ): Promise<BankVerificationResponseDto>;

  getStatus(): Promise<BankVerificationProviderStatusDto>;
}
```

#### Key Types & DTOs
- `BankVerificationMode`: Discriminated union of `"SANDBOX_SIMULATED"` vs `"PRODUCTION_LIVE"`.
- `BankVerificationOutcome`:
  - `SANDBOX_MATCH`: Synthetic core ledger confirms deposit balance and active lien.
  - `SANDBOX_MISMATCH`: Synthetic core ledger reflects conflicting balance or holder name.
  - `SANDBOX_NOT_FOUND`: Synthetic reference does not exist on bank register.
  - `INCONCLUSIVE`: Record requires manual branch confirmation or paper reconciliation.
  - `UNAVAILABLE`: Upstream core banking service is temporarily offline or in maintenance.
  - `NOT_CONFIGURED`: Production adapter is deployed without authorized credentials.
  - `EXTERNAL_VERIFIED`: Reserved **exclusively** for live, authenticated, institutional banking providers.
- `BankVerificationComparisonItem`: Detailed comparison breakdown between submitted FDR fields and bank ledger fields (`fdrNumber`, `amount`, `bankName`, `ifscCode`).

### 3. Deterministic Sandbox Implementation

The sandbox provider (`SandboxBankVerificationProvider` in `src/lib/fdr/bankVerificationProvider.ts`) operates on curated synthetic fixtures representing major Indian commercial and public sector banks (State Bank of India, Punjab National Bank, Bank of Baroda, HDFC Bank, ICICI Bank, Canara Bank).

#### Supported Scenarios:
1. **MATCH**: Core banking ledger confirms exact deposit amount, issuing branch IFSC, active non-encumbrance status, and lien marked in favor of the regulatory body.
2. **AMOUNT_MISMATCH**: Core banking ledger confirms the deposit receipt number exists, but reflects an encumbered balance differing from the submitted document (simulating forged deposit inflation).
3. **NOT_FOUND**: Instrument reference is absent from the core banking register (simulating completely fictitious instrument numbers).
4. **INCONCLUSIVE**: Deposit ledger entry indicates branch-specific paper lien records or legacy ledger states requiring physical branch letter confirmation.
5. **UNAVAILABLE**: Simulates core banking maintenance downtime (HTTP 503 equivalent).
6. **TIMEOUT**: Simulates core banking gateway latency SLA breach (>3000ms).

#### Mandatory Non-Authenticity Disclaimers
Every single sandbox response includes:
- `verificationMode: "SANDBOX_SIMULATED"`
- Explicit disclaimer string:
  > *"SIMULATION NOTICE: This verification was generated by the FDR Guardian AI Sandbox Gateway using deterministic synthetic fixtures. It does NOT represent a live bank confirmation and MUST NOT be used to authorize the release or discharge of any financial instrument."*

### 4. Production Adapter Boundary & Integration Pathway

To avoid anti-patterns such as calling mock external URLs or embedding placeholder credentials in production code, FDR Guardian AI provides an unconfigured production adapter (`UnconfiguredProductionBankProvider`).

```typescript
export class UnconfiguredProductionBankProvider implements BankVerificationProvider {
  readonly providerKey = "production-bank-gateway";
  readonly providerName = "Institutional Core Banking Gateway (Live Production)";
  readonly mode: BankVerificationMode = "PRODUCTION_LIVE";

  async verifyInstrument(params: BankVerificationRequestParams): Promise<BankVerificationResponseDto> {
    return {
      correlationId: `PROD-GATEWAY-${Date.now()}`,
      providerKey: this.providerKey,
      verificationMode: "PRODUCTION_LIVE",
      outcome: "NOT_CONFIGURED",
      verifiedAt: new Date().toISOString(),
      durationMs: 0,
      comparisons: [],
      error: {
        code: "PROVIDER_NOT_CONFIGURED",
        message: "Production bank verification gateway requires institutional SFMS / RBI Open Banking API credentials.",
        retryable: false,
      },
      disclaimer: "PRODUCTION ADAPTER UNCONFIGURED: Live bank gateway credentials not provisioned.",
    };
  }
}
```

#### Real Production Integration Checklist:
When connecting FDR Guardian AI to live banking networks in subsequent deployments:
1. **SFMS (Structured Financial Messaging System)**: Implement ISO 20022 message types (`pacs.008` / `camt.053`) for interbank lien-marking confirmations.
2. **RBI Account Aggregator / Open Banking**: Integrate with licensed Financial Information Providers (FIPs) via OAuth 2.0 mTLS and hardware security modules (HSM).
3. **Dual Authorization (Maker-Checker)**: Regulatory Scrutiny Officers initiate queries; Department Nodal Officers authorize external release requests.

### 5. Database Schema & Immutable Audit Trail

#### Schema Model (`prisma/schema.prisma`):
```prisma
model FdrBankVerificationRequest {
  id                     String    @id @default(cuid())
  fdrId                  String
  correlationId          String    @unique
  providerKey            String
  providerMode           String    // "SANDBOX_SIMULATED" | "PRODUCTION_LIVE"
  requestedFdrNumber     String
  requestedAmount        Decimal   @db.Decimal(12, 2)
  requestedBankName      String
  requestedIfsc          String
  status                 String    // "SUCCESS" | "MISMATCH" | "NOT_FOUND" | "INCONCLUSIVE" | "ERROR" | "TIMEOUT"
  responseOutcome        String    // BankVerificationOutcome
  comparedFieldsJson     String?   @db.Text
  verifiedAmount         Decimal?  @db.Decimal(12, 2)
  verifiedBankName       String?
  verifiedAccountStatus  String?
  isLienConfirmed        Boolean?
  disclaimer             String?   @db.Text
  inconclusiveReason     String?   @db.Text
  errorCode              String?
  errorMessage           String?   @db.Text
  durationMs             Int?
  requestedByUserId      String
  requestedByUserName    String
  requestedByUserRole    String
  createdAt              DateTime  @default(now())

  fdr FdrInstrument @relation(fields: [fdrId], references: [id], onDelete: Cascade)

  @@index([fdrId])
  @@index([correlationId])
  @@index([createdAt])
  @@map("fdr_bank_verification_requests")
}
```

#### Audit Ledger Lineage:
Every inquiry triggers an immutable record in `FdrAuditLog`:
- `action`: `"BANK_VERIFICATION_REQUESTED"`
- `performedBy`: Scrutiny Officer user ID and role
- `metadataJson`: Contains correlation ID, provider mode, requested fields, response outcome, and latency.
